## 摘要

本项目实现了一个面向游戏排行榜场景的多副本分布式 KV 存储：三副本全复制、
state-based 异步复制（周期 gossip）、WAL 持久化、可选 quorum 读写与 CAS。
核心设计是将"当前分数"替换为**不可变加分条目的集合**（grow-only set 型 CRDT），
使合并操作退化为按 `request_id` 求并集——幂等、交换、结合，
从而在一次设计内同时化解消息重复、乱序、分区分歧、崩溃恢复与热点写集中五类故障。
我们构建了可控网络代理（可注入延迟、乱序、重复、双向分区、响应丢失）
与实时可视化演示台，对题目要求的九个故障 topic 逐一执行
"预测 → 注入 → 观察 → 解释"的验证流程，全部演示均通过程序化断言（9/9 PASS）。
报告还给出 quorum 语义的鸽笼推导、happens-before 分析、物理时钟不可依赖性的
现场反例，并如实讨论系统局限与改进方向。

**关键词**：最终一致性；CRDT；异步复制；热点分片；quorum；故障注入

## 1 问题定义

### 1.1 场景与需求

游戏排行榜（全服玩家分数排名）具有三个鲜明的负载特征：

1. **写入量巨大**。每次击杀、拾取都是一次加分，写入 QPS 高出订单、发帖类业务
   一到两个数量级；
2. **可容忍短暂读旧值**。榜单晚几秒更新不产生用户可感知的损失——
   这是业务授予设计者的"宽容额度"；
3. **热点 key 集中**。头部主播、工作室账号的单 key 请求可占比 50% 以上。

对应的正确性要求：**最终一致性**——分区、宕机等故障愈合后，
有限时间内各副本收敛到相同状态；期间允许读到旧值，但**已确认的写入不得丢失**
（持久化承诺），**重复的投递不得重复计分**（幂等承诺）。

### 1.2 难题的来源

单机存在写吞吐上限与单点故障两个死穴，多副本是必然选择；
但数据一旦分布在多台机器，三条"物理定律"立即生效：

- **机器会挂**：副本宕机是常态事件而非意外；
- **网络会坏**：不止断链，还有延迟、乱序、重复投递与响应丢失；
- **时钟不可信**：NTP 校时回跳、闰秒、虚拟机暂停都会让物理时间倒退。

因此真正的难题是：**在会挂、会乱、会跳的世界里，让三份数据最终变成"一份"**。
这是 CAP 定理的范畴：分区发生时必须在一致性（CP）与可用性（AP）之间取舍。

### 1.3 我们的取舍

本场景明确允许短暂旧值，因此选择 **AP + 最终一致性**：
分区期间各侧继续接受写入，愈合后自动收敛。
需要线性一致的操作（CAS）单独提供 quorum 模式（W=2 两阶段提交），
以分区期间少数派不可用为代价换回线性性——按需付费，而非全局买单。

## 2 相关背景

**CAP 与最终一致性。** Gilbert & Lynch（2002）形式化了 CAP 的取舍；
Dynamo（DeCandia et al., 2007）展示了以最终一致性换高可用写入的工程路线，
其 hinted handoff 与 anti-entropy 思想即本文 gossip 恢复机制的原型。

**CRDT。** Shapiro et al.（2011）提出无冲突复制数据类型：
若副本状态构成 join-semilattice（合并满足幂等、交换、结合），
则任意顺序的合并必然收敛。本文的"不可变条目集合 + 求并集"
即 grow-only set（2P-Set 的增长半部）的直接应用。

**逻辑时钟与因果。** Lamport（1978）指出分布式系统中事件的先后
应由通信（happens-before）而非物理时钟定义；向量时钟（Mattern, 1989）
给出因果并发的判定工具。本文在理论分析与演示解释中使用这些概念。

**WAL。** 预写日志是数据库持久化的经典手段：先追加落盘再确认，
崩溃后重放恢复；重放幂等性由日志记录的确定性主键保证。

## 3 系统设计

### 3.1 总体架构

```
                 +------------------+
   demos(client) |  net-proxy :9000 |   故障注入点：延迟/乱序/重复×3/分区/吞响应
                 +--------+---------+
                          |  X-Target-Node 显式转发
        +-----------------+-----------------+
        |                 |                 |
     node1             node2              node3
   [条目集+WAL]  gossip [条目集+WAL]  gossip [条目集+WAL]
```

- **存储节点**（×3，FastAPI 单 worker 容器）：持有条目集、WAL、
  客户端 API（write/cas/score/top/lww）与内部 API（merge/snapshot/两阶段）；
- **net-proxy**：所有节点间与客户端→节点流量的必经之路，
  内置规则引擎（REST 控制），是全部网络类故障的注入装置；
- **gossip 复制**：每节点每秒向全部 peer 推送本地条目集（state-based push）；
- **演示台**：浏览器单页应用，轮询节点状态，含拓扑可视化与注入控制台。

单线程事件循环是刻意选择：单节点写处理天然串行，
CAS 的"检查-追加"原子性直接建立其上，无需额外锁协议（热点演示中另加
per-key 锁模拟磁盘串行）。

### 3.2 数据模型：条目集 CRDT（核心设计）

不给玩家存"当前分数"，而是存**加分事件**：

```
Entry := (request_id, player, delta, ts, node)     # 不可变
score(player) = Σ entry.delta                       # 求和
merge(A, B) = A ∪ B                                 # 按 request_id 并集
```

`request_id` 由客户端生成（UUID），是全系统唯一的幂等键。
该设计把开篇列出的全部网络故障转化为无害：

| 故障 | 攻击面 | 化解机制 |
|---|---|---|
| 重复投递 ×3 | 复制协议 | 并集幂等：同一 request_id 只计一次 |
| 乱序到达 | 复制协议 | 并集交换律：与顺序无关 |
| 分区分歧 | 收敛性 | 愈合后并集 = 两侧之和 |
| 崩溃丢内存 | 持久化 | 条目追加 WAL，重放即恢复 |
| 写热点 | 吞吐 | 条目在任意副本产生均合法 → 写并行度 = 副本数 |

收敛性不依赖测试经验，而是 join-semilattice 结构的数学性质
（`store.py` 另附 200 轮随机乱序/重复合并的自测断言）。

### 3.3 读写路径与 CAS

- **写**：任意副本本地插条目（WAL fsync 后即返回确认），
  异步 gossip 扩散。写入确认语义 = **1 个副本已持久化**（明码标价，
  换取最短确认路径；更强保证走 CAS quorum）。
- **读**：默认本地读（可能旧值，场景允许）；quorum 读 R=2：
  并发读两个副本取新值，**降低但不消除**旧值概率（未实现 read-repair）。
- **CAS**：`score(player)==expected` 则追加条目。两种模式：
  - *local*：静态 primary（key 的一致性哈希映射）单点串行检查。
    分区下客户端访问非 primary 副本时副本就地执行，可能出现双成功——
    这是已知且演示的线性一致性违反（§4.7）；
  - *quorum*：pre-write 暂存至 ≥W=2 个副本确认后 commit，否则 discard。
    分区少数派凑不齐票即拒绝，恢复线性性，代价是少数侧不可用。

### 3.4 持久化、迁移与时钟

- **WAL**：每条提交先追加 JSON 行再 fsync；重放按 request_id 去重；
  尾部残缺行按标准 WAL 语义截断。`/admin/wal` 可运行时关闭以做对照实验。
- **迁移**：新节点从 seed 分页拉取全量条目（游标 = request_id 字典序），
  中途崩溃重启后重拉——条目不可变保证迁移幂等、可重入；
  迁移是新节点自身的故障域，不影响老副本服务。
- **时钟**：节点逻辑时钟 = 系统时间 + 可注入偏移（`/admin/clock`）。
  主路径合并不读时间戳；另设 LWW 寄存器字段作反例演示（§4.8）。

### 3.5 故障注入装置

net-proxy 按规则匹配（源/目标支持通配）执行五种动作：
`delay`（固定或随机延迟，后者即乱序）、`duplicate ×N`、
`partition`（双向黑洞挂起）、`drop_response`（转发成功但吞掉响应）。
规则经 REST 增删，演示台一键操作。压测流量直连节点宿主端口，
避免代理成为吞吐瓶颈（代理是实验装置而非被测系统）。

## 4 故障分析与演示（九个 topic）

每个演示遵循统一协议：**预测 → 注入 → 观察 → 解释**
（违反了哪项保证，或为什么仍然正确）。
以下结果均为 Docker 环境（3 节点容器 + named volume WAL）实测输出。

### 4.1 副本突然宕机

- **预测**：宕机期间写入继续成功；重启后 gossip 反熵自动补齐。
- **结果**：kill node3 期间写 10 次全部成功；start 后三副本收敛
  `score==30`。**PASS**。
- **解释**：异步复制下副本可暂时落后，可用性不依赖单副本；
  恢复由周期 state merge 完成，无人工干预。未违反承诺：
  收敛前该副本的读为旧值，属场景允许窗口。

### 4.2 双向分区 + 消息重复三次

- **预测**：分区期间两侧各写 10 分、各自视图只见本侧；
  愈合时 gossip 消息被复制三份投递，但收敛值 = 20，不多算。
- **结果**：愈合后三副本 `score==20`。**PASS**。
- **解释**：并集按 request_id 去重，重复投递零效果——
  幂等性使 at-least-once 投递语义变得安全。

### 4.3 延迟 10 秒乱序到达

- **预测**：延迟窗口内读到旧值；全部到达后收敛，终值与顺序无关。
- **结果**：窗口内 node2 读旧值；10s 后 `node2==15`。**PASS**。
- **解释**：并集满足交换律。对照：若复制的是"加 10"这类操作指令，
  乱序与重复都会造成多加/漏加——我们在数据结构层面规避了该类缺陷。

### 4.4 节点重启丢失内存状态

- **实验设计**：用分区将数据隔离为 node3 单副本，排除 peer 恢复干扰；
  对照 WAL 开/关。
- **结果**：WAL 开：写 10 → 重启 → 10 条全部恢复；
  WAL 关：再写 5（仅内存）→ 重启 → 仅恢复 10，丢失 5。**PASS**。
- **解释**：写确认必须对应已持久化，否则"确认后丢数据"违反持久化承诺；
  WAL 尾部残缺行被截断是标准处理。

### 4.5 新节点迁移到一半宕机

- **结果**：node4 分页迁移至中途被 kill，期间老集群写入 20/20 成功；
  重启重拉后 `node4.total(495) == node1.total(495)`。**PASS**。
- **解释**：迁移的故障域隔离在新节点；条目不可变使迁移天然幂等。

### 4.6 某 key 占据 50% 请求（热点）

- **实验设计**：对照组将热点 key 全部写压至 primary
  （per-key 锁 + 5ms 模拟磁盘串行）；实验组同批写随机散至三副本。
  8 并发 × 150 写，50% 打热点 key。
- **结果**：热点写中位延迟 **142.0ms vs 46.8ms，差 3.0×**
  （≈副本数并行度）；两组分数均准确（600/600）。**PASS**。
- **解释**："任意副本可收写"即本系统的热点分片——不迁移 key，
  写并行度直接等于副本数；正确性由条目并集保证。

### 4.7 两个客户端同时 CAS

三场景（各用独立 player，基础分 100）：

| 场景 | 模式 | 结果 | 判定 |
|---|---|---|---|
| 健康，都发 primary | local | 恰 1 成功 → 110 | 单点串行，表现线性 |
| 分区，两侧各发 | local | 双成功 → 120 ≠ 110 | **违反单对象线性一致性**（主动演示） |
| 分区，两侧各发 | quorum W=2 | 恰 1 成功 → 110 | 线性性回归，少数侧不可用 |

**PASS**。场景 2 中两个 CAS 互不 happens-before（并发），
两条 CAS 条目均在并集中保留（资金不丢、可审计，但"多了"）；
需要严格线性的调用方应使用 quorum 模式。**CAP 的代价被明码标价并现场交易。**

### 4.8 系统时间倒退一分钟

- **对照实验**：A 路径 LWW 寄存器（按物理时间戳决胜）：
  node1 写 v3 后，node3 时钟 −60s 再写 v4 → v4 时间戳"来自过去"，
  合并后终值停留 **v3**——新写丢失且不可检测。**PASS（反例成立）**。
  B 路径条目集主路径：node3 时钟倒退后照常加分，
  三副本无损收敛至 10。**PASS**。
- **解释**：物理时钟不可比较且会回跳；本系统正确性路径零时钟依赖，
  时间戳仅作元数据。这是"为什么不能只用物理时钟解决冲突"的现场证明。

### 4.9 磁盘写成功、响应在途中丢失

- **结果**：proxy 吞掉 node2 写响应 → 客户端超时；数据已落盘（他副本可见）。
  清除规则后客户端**同一 request_id** 重试 → 响应 `duplicate=true`，
  最终 `score==7` 而非 14。**PASS**。
- **解释**：at-least-once 网络 + 幂等写入 = effectively-once 语义；
  幂等键是客户端生成的 request_id。

## 5 讨论

### 5.1 quorum 的数学语义

N=3、W=R=2 时 W+R=4>3，由鸽笼原理，任意写多数派与读多数派必有交集，
故 quorum 读至少命中一个见过新写的副本。但须诚实界定**未**做到的：
quorum 读取 max 而不做 read-repair，是"大幅降低旧值概率"而非线性读；
W=1 则 1+2>3 失效，"写成功但读不到"成为合法执行——
quorum 的每个数字都是鸽笼的推论，不是调参。

### 5.2 并发写与数据结构选型

面对并发写（互不 happens-before），系统只有三条路：
报错（共识拒绝一方）、仲裁（LWW 时间戳，丢更新且时钟不可靠）、
都要（CRDT 并集）。加分是纯增量语义，并发本就该都保留，
条目集在数学上恰好实现该语义；CAS 是读改写，并发下无安全合并函数，
故必须 quorum 或接受违反。**数据结构选型即提前回答"并发怎么办"。**

### 5.3 局限与改进

| 局限 | 影响 | 改进 |
|---|---|---|
| gossip 全量推送 | 百万条目级代价不可接受 | Merkle 树差异检测、增量反熵 |
| 无 read-repair | 旧值窗口 ≈ gossip 周期(1s) | 读时补新 |
| 存储 ×3 全量冗余 | 空间成本 | 冷热分层、日志重建 |
| CAS quorum 为简化两阶段 | 无 leader 选举/日志复制 | 生产换 Raft |
| 节点间无认证 | 恶意节点可伪造条目 | request_id 签名、准入 |

前两项只影响收敛速度，不影响正确性——"最终"本就是时间参数。

### 5.4 方法论一课

本项目最大收益来自一个决定：**把"当前值"换成"事件集合"**。
它使九种故障从九个独立的工程难题，变成同一个数学性质
（幂等交换并集）的九次复读——设计阶段的正确性投资，
回报在每一个故障场景中被反复兑现。

## 6 结论

我们实现了游戏排行榜场景的最终一致性分布式 KV：
条目集 CRDT 数据模型、state-based 异步复制、WAL 持久化、
任意副本写入（热点分片）、双模式 CAS、可控故障注入与实时可视化。
题目要求的九个故障 topic 全部通过"预测-注入-观察-解释"流程的
程序化断言验证（Docker 环境 9/9 PASS），
其中演示 7 主动展示并解释了线性一致性违反及 quorum 的修复代价，
演示 8 给出物理时钟不可依赖的现场反例。
系统与全部演示可经 `docker compose up` 一键复现。
