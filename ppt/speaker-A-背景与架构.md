## 0:00–0:40 · 开场（PPT 1–2 页：封面 + 场景）

大家好。我们做的项目是一个**游戏排行榜服务**——就是游戏里那个"全服玩家分数排名"的榜单。

它看起来简单，但其实是存储系统里最难伺候的场景之一，三个特点：

1. **写入量巨大**——每个玩家每杀一个怪、每捡一个金币都是一次加分，QPS 比下单、发帖高一到两个数量级；
2. **允许短暂读到旧值**——你在榜上比对手晚几秒更新，没人会投诉，这是业务给的宽容；
3. **热点 key**——头部主播、代练工作室的账号，一个 key 能占一半请求。

这三条合起来，就是我们的题目设定：**高写入、可容忍旧值、热点集中**。

## 0:40–1:40 · 难题从哪来（PPT 3–4 页：单机不行 → 多副本的代价）

为什么这不是"一个 MySQL 加个索引"的事？

单机有两个死穴：**写入能力有物理上限**（一台机器的磁盘和网络封顶），和**一宕机全服榜单消失**（单点故障）。

答案看起来很自然：**加机器，多副本**。但一旦数据存在多台机器上，三个新的难题自动出现，躲不掉：

- **机器会挂**：三台机器，一年内挂一次几乎是必然事件；
- **网络会坏**：不只是断，还会**延迟、乱序、重复投递**——机房交换机不保证消息准时、按序、恰好一次到达；
- **时钟不可信**：每台机器有自己的表，NTP 校时会跳、会倒退。

所以分布式存储的真正难题不是"把数据存多份"，而是：**在副本会挂、消息会乱、时钟会跳的世界里，怎么让三份数据变成"一份"**。这就是经典的 CAP 取舍——分区发生时，你要一致性（CP）还是要可用性（AP）。

## 1:40–2:10 · 我们的选择（PPT 5 页：AP + 最终一致性）

我们的场景有一个别人没有的优惠条件：**业务允许短暂读旧值**。

所以我们大胆选了 **AP + 最终一致性**：分区期间两侧都继续接受写入，允许暂时不一致，分区愈合后自动收敛到同一个值。

这句话说起来一句话，做起来是整个系统。接下来讲我们怎么做的。

## 2:10–4:30 · 核心设计：条目集 CRDT（PPT 6–7 页）

我们全部设计的基石是一个看起来很朴素的决定：

> **不给玩家存"当前分数"这个数字，而是存"加分事件的集合"。**

每次加分是一条不可变的条目：`(request_id, 玩家, 加多少, 时间戳, 哪个节点收的)`。
玩家的分数 = 把他的所有条目加起来。**用 Git 的类比：我们不存文件，我们存 commit 历史。**

复制和合并的规则也只有一条：**两个副本合并 = 条目按 request_id 求并集**。

就这么一个数据结构，把我们前面列的所有故障**一次性**变成无害：

| 故障 | 为什么变得无害 |
|---|---|
| 消息重复投递三次 | 并集里同一条目只算一次 —— **幂等** |
| 消息乱序到达 | 并集不关心顺序 —— **交换律** |
| 节点重启丢内存 | 条目提前写进 WAL 日志，重放即恢复 |
| 分区两侧各自写入 | 愈合后并集 = 两侧之和，**自动收敛** |
| 任何副本都能收写 | 条目在哪个节点产生都合法 —— 这就是**热点分片** |

这个数据结构学术上叫 **CRDT（无冲突复制数据类型）**中的 grow-only set 变体。我们的报告里给了它 200 行 Python 实现和收敛性的随机测试。

## 4:30–5:30 · 系统架构（PPT 8 页：架构图）

具体到实现，架构是四层：

- **三个存储节点**：每个是一台独立的"服务器"（Docker 容器），存条目集、写 WAL 日志、对外提供加分/查询/CAS 接口；
- **gossip 异步复制**：每个节点每秒把自己的条目集推给邻居，互相求并集——数据在后台流动，不等它确认就返回写入，这就是"异步复制"；
- **可控网络代理**：所有节点之间的流量都经过它，它可以按指令**延迟 10 秒、乱序、复制三份、直接黑洞（分区）、吞掉响应**——它是我们的故障注入实验装置；
- **演示台**：一个网页实时显示每个节点的状态和数据流动，等下演示时大家会看到。

读分两级：默认**本地读**（快，可能旧），可选 **quorum 读**（问两个节点取新的，旧值概率低）。CAS 操作有对应的 primary 节点串行处理，也有 quorum 模式——这些细节交给第三位讲。

# 老师可能追问（李祈衡的部分）

**Q1：为什么不用 Paxos/Raft 这样的共识算法？**
A：共识算法是 CP 方案——分区时少数派不可写。我们的场景题目明确允许读旧值，加分操作用共识会在分区期间损失写入可用性，不划算。条目集 CRDT 让加分操作在任意副本本地生效，天然无冲突。但 CAS 这种需要"检查再写入"的操作确实需要线性性，所以我们对它单独提供了 quorum 模式（两阶段：pre-write 确认 ≥2 再 commit）——相当于给需要共识的操作单独开了一条简化共识通道，按需付费。

**Q2：gossip 全量推送，数据量大了怎么办？**
A：演示规模（几千条目）完全没问题。生产规模会换增量同步：用版本向量或 Merkle 树检测差异，只传差集；或者 op-log 加周期 checkpoint。我们选全量推送是因为实现简单、正确性一目了然——它把"收敛"简化成了"求并集"这一个可证明的操作。

**Q3：热点分片和传统的 hash 分片有什么区别？**
A：传统 sharding 是把**不同的 key 拆到不同节点**，一个 key 的写入仍然只在一个节点上，热点 key 还是热点。我们是**同一个 key 的写在任意副本本地生效**——因为条目在哪产生都合法，副本各自记账，靠 merge 收敛。写并行度直接等于副本数，不需要任何路由层。代价是每个副本都存全量数据（存储 ×3），这是空间换写吞吐。

**Q4：为什么选 Python？性能够吗？**
A：课程作业的评分点是分布式语义的正确性，不是单机吞吐。Python + asyncio 单线程事件循环反而带来一个好处：单节点上的写处理天然串行，简化了并发推理（CAS 的原子性就直接建立在它上面）。性能敏感的生产系统会换 Go/Rust，但架构和数据结构原样适用。
